# v0.2-beta

## 2026-10-27

### Saved questions check themselves, and RepoLens watches itself

#### Added
- After an index finishes and the code or documents actually changed, the workspace's saved questions run by themselves (a free retrieval run, no model). Several repositories finishing together give one run, two minutes after the last stops indexing. The Quality page says "ran by itself after indexing", and the server log warns when questions that used to pass now fail. An index that found nothing new, or a workspace with no saved questions, starts nothing. Turn it off with `REPOLENS_AUTO_QUALITY_CHECKS=false`; change the wait with `REPOLENS_AUTO_QUALITY_DELAY_S`.
- Insights → RepoLens health (admins): every background job (daily re-index, old-record clean-up, connected sources, stuck investigations, server readings, unused clones) as ok, waiting, late or failing with its last run and last error; repositories by status; the last saved-question result; and a plain-language list of what needs attention. Also `GET /api/metrics/health`.
- New `/metrics` series for dashboards and alerts: index runs, duration and retries; answers by mode and whether they came from memory, with their duration; model tokens (this counter existed but was never filled in); saved-question runs and the latest pass ratio; repositories by status; and, per background loop, when it last finished and how often it raised. Alert examples are in `docs/operations.md`.

#### Changed
- `golden_runs` gains a `trigger` column (`manual` or `reindex`).

#### Fixed
- A background loop that never started, or stopped, was invisible: the old-record sweeper once never ran and nothing showed it. Every loop now registers up front, so a loop that does not run shows as late.

#### Upgrade notes
- Run the migrations (`alembic upgrade head`, revision 0026). Nothing to re-index. Automatic runs are visible to admins only, like any run whose files were found without a person's access limits.

### Big repositories get time to read their history

#### Fixed
- OpenSSL failed to index with "git log timed out". Reading history uses `git log --numstat`, and in a blob-less clone git downloads the files each commit changed while it runs, so a big repository needs far longer than the 120 seconds every git call was given. Reading the history now gets `REPOLENS_GIT_HISTORY_TIMEOUT` (900 seconds by default); other git calls keep 120. Indexing a big repository is still limited by the network, not by CPU or memory.

#### Upgrade notes
- None. The next index of a repository that failed this way, or the daily check, picks it up.

### The combined graph shows every repository, not just the biggest

#### Fixed
- Choosing "All sources" in the graph showed 116 nodes of one repository and only 4 of another, although the second showed about 150 on its own. The server took the 120 most-connected nodes across everything at once, so a more connected repository crowded the rest out. With several repositories, each now gets its own share of the nodes and the total grows with their number (a share of 120 each, at most 400 in all); a smaller repository that does not fill its share leaves the room to the most-connected of the others. One repository behaves as before: its 120 most-connected nodes.

#### Upgrade notes
- None. The nodes are chosen when the graph is requested; there is nothing to re-index.

### The graph shows one world per repository

#### Changed
- With more than one repository, the graph gives each its own labelled region (name and node count). Repositories that are connected are drawn nearer to each other and unrelated ones apart, and a link that crosses from one repository into another is an amber dashed **bridge** you can hover to read. Before, every repository was pulled into one blob around the centre, so it looked like a single repository.
- Fit to screen leaves room for the names. A single repository looks as before.

#### Upgrade notes
- None. The graph is laid out in the browser; there is nothing to re-index.

### Failed indexes try again, changed repositories are re-indexed daily, and failures say why

#### Added
- **Automatic retry.** When an index fails with something that can pass by itself (a timeout, a dropped connection), RepoLens tries again after 1 minute and again after 5 (`REPOLENS_INDEX_RETRY_DELAYS`, in seconds; empty turns it off). A wrong path, address, branch or password is not retried. The retry only runs if the repository is still in the error state.
- **Daily re-index of what changed.** Once a day (`REPOLENS_AUTO_REINDEX_HOURS`, 24; 0 turns it off) each repository is checked cheaply (`git ls-remote` for a clone, the branch head for a local path), and only those that changed, whose last index failed, or that were cut short by a restart are indexed again. Unreachable ones wait for the next pass.
- **The real reason on the Repositories page.** A failed repository now shows what failed, for example "git log timed out", with a note that timeouts are retried. It used to say "check the path/URL" whatever the cause. A ready repository says it is checked daily.

#### Fixed
- The daily **retention sweep** (old feedback, audit events, ended sessions, used links) was written but never started with the server, so it only ran from its manual endpoint, although `SECURITY.md` and the operations guide say it runs daily. It now starts with the server.
- A repository stuck on "indexing" after the server was restarted in the middle of an index is picked up by the daily pass after three hours.

#### Upgrade notes
- None. No migration. Both settings have defaults.
